## `nius/backend/src/auth/auth.service.ts`

### [P0 / BLOCKER] Статический `redirect_uri=postmessage` не соответствует GIS Code Model popup и не может обслуживать оба origin

**Строки:** `33-46`; связанные места: `backend/.env.example:4`, `backend/src/auth/auth.controller.ts:85-97`, `web-sparkle-shop/src/components/OnboardingForm/GoogleLoginAction.tsx:67-73`, `nius/frontend/src/hooks/useAuthActions.ts:25-45`, `nius/docs/deployment.md:25-36,220-231,688-689`.

```ts
async exchangeCodeForUserInfo(code: string): Promise<GoogleUserInfo> {
  const redirectUri = this.config.getOrThrow<string>('GOOGLE_REDIRECT_URI');
  // ...
  body: new URLSearchParams({
    code,
    // ...
    redirect_uri: redirectUri,
  }),
}
```

Оба клиента используют `useGoogleLogin({ flow: 'auth-code' })`, то есть GIS вызывает `initCodeClient` в popup-режиме. Согласно текущей официальной документации Google, в popup-режиме переданный клиентом `redirect_uri` игнорируется, а код привязывается к **origin страницы, вызвавшей `initCodeClient`**. При серверном обмене нужно передать тот же origin. Источники: [Use Code Model](https://developers.google.com/identity/oauth2/web/guides/use-code-model#get_access_and_refresh_tokens), [Google Account Authorization JavaScript API](https://developers.google.com/identity/oauth2/web/reference/js-reference#CodeClientConfig).

Текущий backend всегда отправляет одно значение, а код теперь получается как минимум с `https://app.nius.cz`, `https://www.nius.cz`, `https://nius.cz`, `http://localhost:5173` и `http://localhost:8080`. Значение `postmessage`, добавленное в `.env.example` и закреплённое в документации, не является origin ни одного из этих вызовов. Результат — token endpoint может отклонить код как `redirect_uri_mismatch`/`invalid_grant`; controller скрывает первопричину за общим `401 Google auth failed`. Совпадение client ID на фронтендах и успешные CI-сборки этот контракт не проверяют.

**Исправление:** передавать origin вызвавшей страницы в `/auth/google` (либо извлекать HTTP `Origin`), строго проверять его по объединённому allowlist `FRONTEND_ORIGIN` + `LANDING_ORIGINS`, и только затем передавать это значение в `exchangeCodeForUserInfo(code, validatedOrigin)`. Нельзя принимать произвольный `redirectUri` без allowlist-проверки. Удалить указания про `postmessage` из `.env.example`, README/CLAUDE/deployment docs. На сервере логировать безопасный код/статус ошибки token endpoint без `code`, access token и тела профиля.

Добавить unit-тест `AuthService` с mocked `fetch`, который проверяет точный `redirect_uri` в `URLSearchParams`, и HTTP integration-тест для обоих production origins. Текущий `auth.controller.spec.ts:39-47` полностью мокает `exchangeCodeForUserInfo`, поэтому не способен поймать этот blocker.

## `nius/backend/src/cors/scoped-cors.ts`

### [P1 / HIGH security] Неизвестный Origin не отклоняется и может выполнить login-CSRF через простой form POST

**Строки:** `69-105`, особенно `96-105`; связанные места: `backend/src/main.ts:25-26,47`, `backend/src/auth/auth.controller.ts:83-108` в проверяемом commit.

```ts
if (
  isLandingOrigin &&
  !isLandingPublicRoute &&
  MUTATING_METHODS.has(req.method.toUpperCase())
) {
  res.status(403).json({ code: 'ORIGIN_NOT_ALLOWED' });
  return;
}

next();
```

Запрет применяется только когда Origin уже распознан как landing. Для `Origin: https://evil.example` обе переменные `isAppOrigin`/`isLandingOrigin` ложны, CORS-заголовки не выставляются, но middleware вызывает `next()`. Отсутствие `Access-Control-Allow-Origin` не запрещает браузеру **отправить** simple request; оно лишь запрещает JavaScript читать ответ. Дополнительно `main.ts:26` глобально включает `express.urlencoded`, поэтому auto-submitting HTML form с `Content-Type: application/x-www-form-urlencoded` доходит до `POST /auth/google` без preflight и проходит DTO, если содержит один `code`.

Злоумышленник может получить одноразовый код для своего Google-аккаунта, заставить браузер жертвы сделать top-level/form POST и установить жертве `access_token` злоумышленника. После session swap данные, которые жертва введёт в NIUS, становятся доступны владельцу аккаунта. Это именно тот login-CSRF сценарий, для которого Google в popup Code Model требует custom header и серверную проверку ожидаемого origin: [Google: Protect against CSRF attacks](https://developers.google.com/identity/oauth2/web/guides/use-code-model#protect_against_csrf_attacks).

**Исправление:** для любого mutating request с присутствующим, но неразрешённым Origin возвращать 403 до controller; не ограничивать проверку условием `isLandingOrigin`. На `/auth/google` отдельно требовать точный allowlisted Origin и приложение-специфичный заголовок (`X-Requested-With`/`X-NIUS-CSRF`) с фиксированным значением, чтобы запрос обязательно проходил preflight. Можно также отклонять form-urlencoded для JSON-only auth endpoint. Динамический origin из P0 должен браться только после этой проверки.

Добавить e2e-тест: `application/x-www-form-urlencoded` + `Origin: https://evil.example` → 403, `exchangeCodeForUserInfo` не вызван, `Set-Cookie` отсутствует. Текущий `scoped-cors.spec.ts` проверяет лишь известный landing origin на непубличном route и поэтому не покрывает эту ветку.

## `nius/frontend/src/pages/LoginPage.tsx`

### [P1 / HIGH data-integrity] Кнопка Google доступна до завершения проверки старой сессии

**Строки:** `55-60,109-150,226-232`; связанные места: `frontend/src/context/AuthContext.tsx:8-18`, `frontend/src/hooks/useAuthActions.ts:49-68`.

```tsx
const { user } = useAuth()
// loading из AuthContext игнорируется

<UnstyledButton
  onClick={() => login()}
  disabled={loading} // это только loading useAuthActions
>
```

`AuthProvider` начинает `/auth/me`, но `LoginPage` не учитывает его `loading` и сразу показывает Google CTA. При существующей cookie аккаунта A пользователь может успеть выбрать аккаунт B. Если исходный `/auth/me` вернёт A раньше `/auth/google`, effect на строках `118-150` привяжет capability к A. Последующий вход B получит `409`, но заказ уже оказался у неправильного пациента.

Второй вариант той же ошибки находится в `useAuthActions.ts:49-68`: любой Axios transport error (`!error.response`) объявляется восстановимым, а следующий `/auth/me` может вернуть старую сессию A и затем привязать заказ к ней, хотя пользователь только что выбрал B.

**Security impact:** capability заказа может быть потреблена и заявка может быть связана с другим аккаунтом, чем явно выбранный в Google popup.

**Исправление:** не показывать/не активировать Google login до завершения начального auth probe. AuthContext должен различать подтверждённый `401/403` и сетевую ошибку, а не превращать обе ситуации в `user=null`. В `useAuthActions` восстанавливать через `/auth/me` только при серверно подтверждённом `phase === 'link'`; для безответной transport-ошибки показывать retry, если до popup не был получен свежий подтверждённый anonymous status. Добавить интеграционный тест `AuthProvider + LoginPage + useAuthActions` со старой сессией A и Google-ответом B.

### [P1] `LoginPage` и `useAuthActions` одновременно привязывают заказ и выполняют разные переходы

**Строки:** `118-150`; связанные места: `frontend/src/hooks/useAuthActions.ts:70-119`.

```tsx
useEffect(() => {
  if (!user || authedRedirectHandledRef.current) return
  // второй POST /auth/link-order
  // ...
  window.location.assign(returnTo ?? '/cabinet')
}, [user, returnTo, orderId, orderAccessToken])
```

`useAuthActions` вызывает `setUser(user)` до завершения собственной привязки и навигации. Это запускает effect `LoginPage`, который делает ещё один `/auth/link-order`. После этого hook выбирает `/form` для пациента без intake (`useAuthActions.ts:113-119`), а effect независимо делает полный переход на `/cabinet` (`LoginPage.tsx:124,148`). Async IIFE не отменяется при unmount, поэтому поздний ответ второго link-запроса способен увести уже открытую `/form` обратно в `/cabinet`. Также дважды отправляется `order_linked`.

**Исправление:** оставить ровно одного владельца orchestration. Например, hook выполняет auth/link и возвращает подтверждённый результат, а `LoginPage` единожды выбирает маршрут; либо effect обслуживает только сессию, существовавшую **до** запуска Google flow, и пропускается по ref во время hook-flow. Добавить component/integration-тест на URL `orderId/orderAccessToken` без `returnTo`, проверяющий один `link-order`, один `order_linked` и конечный `/form`.

### [P2] SUPERADMIN попадает в неустранимый цикл ошибки без возможности сменить аккаунт

**Строки:** `152-179`; связанные места: `frontend/src/hooks/useAuthActions.ts:70-79`.

```tsx
if (user) {
  if (loginError) {
    return <UnstyledButton onClick={() => window.location.reload()}>...</UnstyledButton>
  }
}
```

Hook сначала сохраняет SUPERADMIN через `setUser`, затем сообщает `link` error. Единственное действие в error screen — reload. После reload admin-cookie снова восстанавливается, effect снова вызывает запрещённый `/auth/link-order` и возвращает ту же ошибку. Capability теперь сохраняется, но пользователь не может выйти и выбрать PATIENT, поэтому legacy login URL остаётся тупиком.

**Исправление:** добавить явное «Войти другим аккаунтом»: вызвать `/auth/logout`, очистить `user`, не удалять onboarding capability и только затем открыть Google popup. Не использовать reload как retry привязки для заведомо неподходящей роли.

## Production testing и rollout risk

### Порядок выкладки

1. **Не выкладывать текущую пару как завершённый funnel до устранения P0 и login-CSRF.** Сначала исправить динамический, allowlisted popup origin, отказ для неизвестных Origin/custom CSRF header в backend и оба клиента/документацию; добавить server-side диагностирование token endpoint.
2. В Google Console для единого client ID проверить Authorized JavaScript origins: `https://app.nius.cz`, `https://www.nius.cz`, `https://nius.cz`; localhost origins держать только если это допустимо политикой production client, иначе использовать отдельный dev client. Client ID на landing/backend/app должен совпадать.
3. Выложить совместимый backend: CORS + новый link contract + исправленный redirect origin. До landing убедиться, что существующий `app.nius.cz/login` обменивает code и legacy логин без order работает.
4. Выложить исправленный frontend кабинета, чтобы убрать старую-session race, двойную link orchestration и SUPERADMIN dead end.
5. Выложить landing последним. При откате идти в обратном порядке: landing → app frontend → backend, чтобы новый клиент не остался на старом API contract.

### Обязательные smoke cases

1. Новый anonymous пользователь: create → Google PATIENT popup → `/auth/google` 200 + две cookies → подтверждённый link → `location.replace('/form')`; token отсутствует в URL/localStorage.
2. PATIENT с cookie: create возвращает `linked:true`; Google popup не появляется; подтверждается `/auth/me/public`; переход на `/form`.
3. Старая cookie A + выбор Google B в legacy `/login?...`: кнопка недоступна до auth probe; заказ не может быть привязан к A вследствие гонки.
4. Два браузера/два аккаунта на одной capability: ровно один link success, второй 409; `patientId` первого не меняется.
5. SUPERADMIN: create остаётся anonymous; есть рабочий путь «другой аккаунт» без потери capability; admin не становится `patientId`.
6. Popup close, popup blocker, GIS script error, API 401, `phase=link` 409/500 и потерянный response: финал остаётся retryable, повторный клик не создаёт параллельный flow.
7. Закрытие dialog во время linking: либо закрытие запрещено, либо завершение приводит к детерминированному redirect/recovery.
8. Contact me: anonymous capability → 200; отсутствующий/неверный token → 403; `linked:true` ведёт себя согласно выбранному UI/API contract и не показывает гарантированно падающую кнопку.
9. CORS/CSRF: preflight/actual request для `www`, apex и app; form-urlencoded `POST /auth/google` с неизвестного Origin получает 403 без `Set-Cookie`; `POST /intake` с landing origin остаётся без разрешения/403; cookies доступны после перехода `www → app`.
10. Desktop + mobile/Safari: popup, shared `.nius.cz` cookie, Back после `replace`, отсутствие Google script на prerendered homepage до открытия final screen.

### Мониторинг и rollback triggers

- Разделить метрики `/auth/google` по origin и исходу token exchange. Любой всплеск 401, `redirect_uri_mismatch`, `invalid_grant` или отсутствие успешных обменов с `www.nius.cz` — немедленный rollback landing/fix-forward backend.
- Алерты на рост `phase=link` 4xx/5xx, `/auth/link-order` 409/403, `contact-me` 403 и CORS preflight failures.
- Funnel: `login_cta_clicked → login_popup_opened → login_completed → order_linked → /form`. Резкое падение любого перехода, особенно успешный `order_linked` без загрузки `/form`, — rollback trigger.
- Data-integrity query/alert: onboarding orders, привязанные к пациенту в коротком окне после другого Google user selection; а также повторные `link-order` для одной capability из одного browser flow.
- При rollback backend сохранить новый явный link contract либо сначала откатить оба клиента; возврат к молчаливому `200` на неуспешную привязку снова создаст ложные redirects.
